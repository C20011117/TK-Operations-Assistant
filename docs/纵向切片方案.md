## 1. 已确认的前提

| 事项 | 决定 |
|---|---|
| 目标站点 | 全部欧洲 TikTok Shop 市场（见 3.1）。每个找人任务选择一个欧洲站点，切片内不做跨站点聚合 |
| 大模型 | OpenAI 兼容接口（`base_url` + `api_key` + 模型名可配置） |
| 交付形态 | **单机 Windows 桌面应用**（Tauri 2 + Python 后端子进程 + SQLite），双击即用，不依赖 Docker；见 [桌面版架构方案](桌面版架构方案.md) |

| 后端 | Python 3.12 + FastAPI + SQLAlchemy 2 + Alembic；包管理默认 uv |
| FastMoss 接入 | **MCP 为主**（远程 Streamable HTTP）。REST 作为以后可增加的第二个适配器；CSV 人工导入用于无数据站点 |

## 2. 目标与原则

**目标**：用最短路径让 [E2E-01 一个 BD 完成两条新视频并维护达人](architecture/06-verification-and-traceability.md) 在真实代码里走通。前端、后端、数据库、Worker、模型各打通一条线，不追求每个功能模块完整。

**可扩展性原则：后补代价高的现在就做对，后补代价低的先不做。**

| 现在必须做对（以后改要大量返工） | 先简化或推迟（以后按模块加入） |
|---|---|
| 本机接口保护（随机端口 + 启动令牌）+ 密钥存 Windows 凭据管理器 | 注册、邀请、账号恢复、多企业切换 |
| 版本化与不可变快照（产品、条件、推荐、脚本、视频版本） | 文档解析与 RAG 资料库 |
| `jobs` 表 + 租约 + fencing（进程内执行器，重启可恢复） | 调度器、周期刷新、通知 |
| 连接器注册表（固定操作 + schema + 费用） | REST 适配器、多供应方、字段能力矩阵界面 |
| 幂等键 + `action_confirmations`（对外动作由本人确认） | 自动外发渠道（切片内用“人工发送并登记”） |
| 三态硬条件 `pass/fail/unknown`；适配度与证据充分度分开 | 多种发现方式、参考达人扩展、比较视图 |
| 金额 NUMERIC + 币种；时间 UTC + IANA 时区 | 跨站点聚合、汇率换算 |
| 市场目录表 `markets`（平台站点码与供应方地区码分开） | 更多非欧洲站点（加一行目录数据即可） |
| 拍摄轮次与视频版本分开：返修 = 新版本，新视频 = 新轮次 | 受限提交链接、AI 视频分析 |
| 个人数据字段加密与最小化（寄样地址等） | 完整的数据主体请求、删除与导出流程 |
| `usage_ledger` 基本记账 + 单次运行费用上限 | 预占、结算、核对，套餐和账单 |
| 统一运行状态枚举（全部 8 个值先定义好） | 取消后恢复、partial 核对的完整界面 |
| OpenAPI 自动生成 TS 客户端 | 报表、导出、经验规则、数据删除链路 |

判断标准：只要一项会影响**数据库主键和外键、权限边界、历史可追溯、个人数据处理或外部动作的幂等**，就进入切片。

## 3. 欧洲站点处理

### 3.1 市场目录（种子数据，含 2026-09-29 实测）

[02 · 数据模型](architecture/02-data-model.md) 规定站点码“来自平台市场目录，不自动等同 ISO 国家码”。切片建立全局目录表 `markets`，把平台站点码、FastMoss 地区码、币种、时区、内容语言和数据状态分开存放。

实测方法：`creator_search`，条件 `is_ecommerce_creator=true`，按 `day28_gmv` 降序，每站 1 次。

| market_code | 站点 | FastMoss `region` | 实测结果数 | 返回的 `currency` | 结算币种 | 默认时区 | 常见内容语言 | 切片状态 |
|---|---|---|---|---|---|---|---|---|
| `UK` | 英国 | `GB` | 2000（上限） | GBP | GBP | Europe/London | en | 可查询 |
| `DE` | 德国 | `DE` | 2000 | EUR | EUR | Europe/Berlin | de | 可查询 |
| `FR` | 法国 | `FR` | 2000 | EUR | EUR | Europe/Paris | fr | 可查询 |
| `IT` | 意大利 | `IT` | 2000 | EUR | EUR | Europe/Rome | it | 可查询 |
| `ES` | 西班牙 | `ES` | 2000 | EUR | EUR | Europe/Madrid | es | 可查询 |
| `NL` | 荷兰 | `NL` | 2000 | 空 | EUR | Europe/Amsterdam | nl | 可查询，金额币种未知 |
| `BE` | 比利时 | `BE` | 1252 | 空 | EUR | Europe/Brussels | nl / fr | 可查询，金额币种未知 |
| `AT` | 奥地利 | `AT` | 775 | 空 | EUR | Europe/Vienna | de | 可查询，金额币种未知 |
| `PL` | 波兰 | `PL` | 2000 | 空 | PLN | Europe/Warsaw | pl | 可查询，金额币种未知 |
| `PT` | 葡萄牙 | `PT` | 2000 | 空 | EUR | Europe/Lisbon | pt | 可查询；TikTok Shop 是否已开放待确认，界面提示 |
| `IE` | 爱尔兰 | 无 | 0 | - | EUR | Europe/Dublin | en | 仅人工导入 |

规则：

- 任务只保存 `market_code`，调用连接器时再通过目录映射成供应方地区码。**英国必须传 `GB`**：工具说明的示例写 `UK`，但实测传 `UK` 返回 0 条且不报错，容易被误认为“没有达人”。以后接入其他供应方，只需给目录加一列映射，任务数据不变。
- 目录里标为“仅人工导入”的站点，连接器直接拒绝调用，不发出注定为空的请求。
- 返回的 `currency` 按原值保存。为空时金额显示为“币种未知”，不默认当作站点结算币种，也不做换算。
- FastMoss 的 `region` 指**达人所在地区**，不证明达人具备该站点的带货资格。推荐卡上的“带货资格”默认显示为 `unknown`。
- “实测结果数”只说明当天有数据，不代表字段完整；各站点标为“已支持”前仍需完成 M2 的契约测试。
- 一个产品可以针对不同欧洲站点各建一个任务，条件和名单互不影响（规格第 2 节）。

### 3.1a 实测发现的数据质量问题与处理规则

| 现象（2026-09-29 实测） | 处理规则 |
|---|---|
| 同一字段有时是整数、有时是小数（如 `day28_gmv`） | 统一解析为 Decimal；保存原始类型标记 |
| 按 `day28_gmv` 降序时，GB、DE 首条的 GMV ÷ 销量约为每件 9.7 万 GBP / 17.8 万 EUR | 合理性检查：折算单价超出品类合理区间时，观测标记 `anomaly`，推荐卡显示“数据异常，待核实”，不参与排序分数 |
| `total_units_sold = 0` 但 `video_units_sold > 0` | 字段间一致性检查，矛盾时两者都标记 `inconsistent` |
| 多个站点 `engagement_rate_percent = 0` | 0 视为“可能缺失”，按 `unknown` 处理，不当作真实的 0 |
| 部分站点 `currency` 为空 | 金额保存为“币种未知” |
| 空结果与失败都不扣费，但返回形态不同 | 空结果记为 `empty`，错误记为 `failed`，额度不足（402）记为 `insufficient_credits`，界面分别说明 |

排序不能只按单一金额字段降序取前几名，否则异常值会排在最前；发现阶段先取候选池，再经过合理性检查和三态硬条件后排序。

### 3.2 多语言

- `content_brief_versions` 记录 `content_language`，默认取站点的常见语言，BD 可以修改（例如比利时可选 nl 或 fr）。
- 拍摄包先生成目标语言版本，同时附一份中文对照供 BD 检查；发给达人的只有目标语言版本，并以 BD 确认的版本为准。
- 推荐理由和反馈建议默认用中文展示给 BD；发给达人的反馈由 BD 选择语言后生成草稿，确认后再发送。

### 3.3 GDPR 与个人数据（切片最低要求）

欧洲达人的联系方式和寄样地址属于个人数据，从切片起就要做到：

- 寄样地址、电话、邮箱只存在专门字段里，使用应用层加密（信封加密，本地开发用环境变量里的密钥，生产换 KMS）。日志、LLM 上下文和错误信息里都不出现这些字段。
- 发给模型的内容只包含必要信息：推荐判断用公开指标和产品资料，拍摄包用产品版本和达人公开的内容风格，不发送地址和联系方式。
- 模型服务商的数据处理地区和保留政策作为配置项记录（`LLM_DATA_REGION`、`LLM_PROVIDER_DPA_REF`）。上线前确认是否满足企业的 GDPR 要求，切片阶段不作合规承诺。
- 删除达人关系时，个人数据字段必须能单独清空；完整的删除链路以后按 [05 · 安全与运营](architecture/05-security-operations.md) 实现。

## 4. 切片范围：用户能完成的 10 步

每步对应架构中的模块和主要数据表，未列出的表不建。

| 步 | 用户动作 | 模块 | 主要表 |
|---|---|---|---|
| 1 | 首次打开：在“设置”页填写 FastMoss 与大模型的 Key 并通过连通检查（M0-D 已完成） | settings | `app_settings`（Key 本身存凭据管理器） |
| 2 | 填写产品和欧洲站点价格，确认版本 | knowledge | `products` `product_versions` `product_market_terms` |
| 3 | 选择一个欧洲站点建找人任务，设条件与费用上限 | campaigns | `markets` `campaigns` `campaign_markets` `criteria_versions` |
| 4 | 启动匹配，查看进度与推荐卡 | matching / connections | `matching_runs` `jobs` `provider_calls` `provider_snapshots` `candidate_evaluations` `evidence_items` `recommendation_snapshots` `recommendation_items` `usage_ledger` |
| 5 | 保留或排除候选，确认合作 | shortlists / creators / collaborations | `shortlist_decisions` `creators` `creator_relationships` `collaborations` |
| 6 | 确认寄样（人工登记物流与签收，地址加密保存） | collaborations | `sample_shipments` `external_actions` `action_confirmations` |
| 7 | AI 生成目标语言拍摄包，编辑后确认 | production | `content_briefs` `content_brief_versions` |
| 8 | 第 1 轮：上传 V1 → 按时间码给反馈 → 上传 V2 → 验收通过 | production | `production_rounds` `video_assets` `video_versions` `video_reviews` `feedback_items` |
| 9 | 按几个维度分类达人，建维护计划 | creators | `creator_classification_events` `maintenance_plans` |
| 10 | 从维护计划发起第 2 轮，回收新视频；工作台显示待办 | production / automation（只做查询） | 复用以上表；待办由当前状态实时计算 |

**切片验收标准**（从 E2E-01 删减而来）：

1. 两轮计为 2 条新视频，第 1 轮的 V1/V2 只算 1 条。
2. 旧脚本、旧反馈和旧视频版本都能查到。
3. 寄样地址在数据库文件中是密文；把数据库文件单独拷到别的电脑上读不出地址。
4. 重复提交同一个幂等请求，不会重复寄样、重复调用付费接口，也不会重复产生视频。
5. 未知字段在推荐卡上显示为“未知”，不被当作 0 或“符合”。带货资格默认未知。
6. 英国任务显示 GBP、Europe/London，德国任务显示 EUR、Europe/Berlin，两个任务的名单互不影响。
7. 日志和 LLM 请求记录中查不到寄样地址。

## 5. 关键技术决策

### 5.1 数据来源：FastMoss MCP 连接器

**接入方式**：后台 Worker 作为 MCP 客户端，按固定工具清单调用 `https://mcp.fastmoss.com/mcp`（Streamable HTTP）。**不让大模型自己选择 FastMoss 工具**，符合 [00 · 架构决策](architecture/00-decisions.md) ADR-05。

连接器接口 `ProviderOperation`：`name`、`params_schema`、`response_schema`、`credit_cost_estimate()`、`execute(ctx, params)`。内部操作与 MCP 工具的对应关系：

| 系统内部操作 | MCP 工具 | 实测 / 预计扣费 | 阶段 |
|---|---|---|---|
| `account.credits` | `credit_usage_summary` | 0（实测） | M0 连通检查 |
| `creator.search` | `creator_search` | 每次 1 额度，与返回条数无关（实测） | 切片 M2 |
| `creator.profile` | `creator_profile_overview` | 预计 2 额度 | 后续 |
| `creator.audience` | `creator_fans_distribution` | 预计 2 额度 | 后续 |
| `creator.content` | `creator_video_analysis` | 预计 2 额度 | 后续 |
| `creator.products` | `creator_product_list` | 预计 1 额度 | 后续 |
| `video.script` | `video_script_info` | 待实测 | 后续（拍摄参考） |

实测得到的接口规则（2026-09-29）：

- 认证用请求头 `Authorization: Bearer <key>`，**不把 Key 放进网址**；服务器返回 `mcp-session-id`，连接器负责会话建立与失效重连。
- 服务器共 55 个工具，都没有 `outputSchema`；结果是 `content[0].text` 里的 JSON 字符串。连接器必须用自己的 Pydantic schema 校验，校验失败时该能力降级，不把解析不了的数据当成 0。
- 每次结果带 `_meta.charge = {charged, credit_cost, remaining_credits}` 和 `request_id`，直接写入 `provider_calls` / `usage_ledger`，余额显示以它为准。
- 每页最多 10 条，`page` 最大 500，`total` 显示上限 2000。每次调用扣费与条数无关，所以固定取 `pagesize=10`。
- 空结果不扣费；额度不足返回 402，按 `insufficient_credits` 处理并提示充值，不自动重试。
- 限速按套餐（试用和 Basic 为每分钟 40 次）。连接器在进程内做按 Key 的令牌桶限流，超过时排队，不并发冲击。
- 每取一页前都检查任务费用上限和取消状态。

其他适配器：

- **`FastMossRestAdapter`**（以后）：REST 价格按条数计费，大批量搜索时可能更便宜。它与 MCP 实现同一个 `ProviderOperation` 接口，任务按连接能力选择**一种**传输方式，同一逻辑请求不会两条路都试。
- **`ManualImportAdapter`**：导入 CSV 达人名单，用于爱尔兰等没有数据的站点，或者没有 Key 时开发。发现方式记为 `manual_import`，界面提示“非实时数据”。
- **`FixtureAdapter`**：只在 `test` 环境注册，生产配置启动时拒绝加载。自动化测试使用它，不消耗额度。

合规：FastMoss 条款要求对数据保密，不得分享、转让或用于竞品。切片期间不缓存原始响应，只保存规范化快照；多企业共用、云端 LLM 处理和缓存的正式授权在商用前向 FastMoss 书面确认。

### 5.2 匹配流程：用 LangGraph 做最小图

```text
load_context → discover → hard_filter → assess(LLM) → validate → persist
```

- `hard_filter` 是纯代码，只输出 pass/fail/unknown，不交给模型。
- `assess` 用结构化输出，每条判断必须引用 `evidence_id`；`validate` 删掉引用不存在的结论，并标记为模型推断。
- checkpoint 存在本机 SQLite 数据库（`langgraph-checkpoint-sqlite`），只保存执行位置和对象引用，不复制业务数据。
- 以后要加的节点（`enrich` 补查详情、RAG 检索、`waiting_input` 暂停）都插在现有节点之间。
- **M2 实现说明（2026-09-29）**：
  - 实际节点为 `load_context → discover → hard_filter → assess → persist`（`validate` 合并在 `assess` 内：引用不存在或没有引用的结论移入“模型推断（无数据支持）”）。
  - 暂不使用 LangGraph checkpoint：图状态只有 `run_id`，业务数据全部在应用表中，每个节点可重入。应用中断后任务重新排队、整图重跑：已成功（含空结果）的 FastMoss 调用按 `(run_id, 请求哈希)` 直接复用快照，不重复扣费；中断时正在进行的调用记为 `unknown`，不自动重发，本次运行以“部分完成”结束。等加入 `waiting_input` 暂停时再引入 checkpoint。
  - 候选池目标 = 目标名单数 × 3（至少 20、至多 200）；每取一页前检查额度上限和取消。只有“硬条件 + FastMoss 能直接筛选”的字段编进搜索参数，软条件不在源头排除候选。
  - AI 判断最多覆盖前 40 位（或目标数 × 2），每批 5 人、3 批并发；未配置大模型时推荐卡只含规则判断。
  - 人工导入（CSV）与 FastMoss 搜索共用同一套条件判断和推荐卡，爱尔兰等“仅人工导入”站点只能用这种方式。
  - 软条件得分相同时，按条件填写顺序逐条比较（通过 > 未知 > 不通过），决定谁先获得 AI 判断以及推荐卡顺序（`m2-rank-2`）。
- **M2 真实数据验证（2026-09-29，英国 · 榨汁杯 · 目标 5 人 · 额度上限 3）**：
  - 共消耗 FastMoss 3 额度：结构探测 1 次 + 正式运行 2 页（候选 20 人，达到候选池目标后停止）。大模型 10 人 / 2 批，约 8.7k 输入 + 3.0k 输出 token；全程约 3 分钟，其中一批遇到网络错误后自动重试成功。
  - `creator_search` 实测结构：`{total, list:[{creator, commerce_summary, audience_summary}]}`。据此补充的字段对应：`creator_type_code`（1 个人 / 2 店铺）、`video_count_total`、`audience_summary.age_distribution`（18-24 / 25-34 / 35-44 / 45-54 / 55+，合并成搜索参数的三档后取占比最大者）、`creator.category.name` 与 `commerce_summary.trend_categories[].name`（作为“类目”提供给 AI 判断和推荐卡）。
  - 结果不返回 `is_ecommerce_creator`；当搜索参数已要求带货达人时，该条件记为“已知 · 由搜索条件保证”。结果也不返回账号简介。
  - GB 结果币种均为 GBP；互动率大多为真实值（返回 0 的仍按未知处理）。
  - 视频带货销量大于累计销量、近 28 天销量大于累计销量在真实数据中很常见（口径不同），不判为矛盾；只有“累计销量为 0 但视频销量大于 0”才标记为字段矛盾。

#### M2.1 按产品找达人（2026-09-29）

目标：用户的商品是摄像头，推荐的就应该是带过 3C / 安防类商品的达人，而不是只靠用户手填的关键词碰运气。

实测依据（摄像头 · GB，共 5 额度）：
- `search_category_by_words`（不扣费）能把“摄像头 / security camera”对应到 TikTok 商品类目，返回一、二、三级类目编号和中文路径，例如“手机与数码 › 摄影摄像 › 监控摄像设备”。
- `creator_search` 支持 `product_category_l1_id / l2_id / l3_id`（带货商品类目）筛选，按三级类目搜到 446 人；含义是“带过该类目商品”，不等于主营方向（前 10 人中 7 人近期带货类目含 Electronics）。
- `product_search`（1 额度）按类目返回同类在售商品及其近 28 天销量、合作达人数。
- `product_creator_analysis`（3 额度）返回卖过某个商品的达人及其对该商品的销量 / GMV 贡献，但不含近 28 天 GMV、互动率等指标。

设计：
1. **产品确认商品类目**：产品事实新增 `category {l1_id, l2_id, l3_id, path}`，随产品版本确认、不可修改。产品编辑页用产品名称和关键词调用类目识别（免费），用户从候选中选择。找人任务在产品没有类目、也没有关键词时给出警告。
2. **按类目搜索**：找人条件的搜索设置新增“按产品类目搜索”（默认开）和类目层级（三级 / 二级 / 一级，默认三级）。开启后先单独按类目搜索（不带关键词，按近 28 天 GMV 从高到低取）；类目结果取完仍不够时，再按关键词搜索（不带类目）。实测（英国站，监控摄像设备 + “security camera”）类目和关键词叠加返回 0 条，而单独类目有 446 条——关键词匹配的是达人昵称和简介，与类目叠加过窄。
3. **类目匹配显示在推荐卡上**：新增观测“带过本产品类目”——经类目筛选找到或卖过竞品的记为“是”（注明依据），只凭关键词找到的记为“未知”（数据源只返回一级带货类目名称，无法确认）。该观测同时作为 AI 判断的证据；AI 判断的候选选择和推荐卡排序优先考虑“卖过竞品 > 带过本类目 > 未知”。
4. **竞品找达人（可选）**：用户在找人条件中添加最多 3 个竞品（从“推荐竞品”列表中选择——按产品类目和站点调用 `product_search`，每次 1 额度，需用户点击确认；或直接粘贴 TikTok 商品链接 / 编号，免费）。运行时先对每个竞品调用 `product.creators`（每个 3 额度，只取第 1 页），只保留所在地区与本站点一致的达人；然后按竞品 GMV 贡献从高到低，用 `creator.search`（按 uid 精确查询，每人 1 额度）补全近 28 天 GMV、互动率等数据，补全人数不超过目标名单数；最后用类目搜索补足候选池。所有调用都计入本任务的额度上限，达到上限即停止。
5. 竞品推荐不属于某次运行，调用记录写入 `usage_ledger`（`run_id` 为空，operation `product.search`）。

### 5.3 模型：OpenAI 兼容接口

- `platform/llm/gateway.py` 统一封装 `langchain_openai.ChatOpenAI(base_url=..., api_key=..., model=...)`，业务代码只调用 gateway。
- 配置项：

```text
LLM_BASE_URL          例：https://api.openai.com/v1 或任意兼容服务
LLM_API_KEY           本地开发放 .env，生产放密钥存储
LLM_MODEL_MATCHING    推荐判断使用的模型
LLM_MODEL_BRIEF       拍摄包生成使用的模型
LLM_STRUCTURED_MODE   json_schema | function_calling | json_mode
LLM_TIMEOUT_SECONDS
LLM_MAX_TOKENS_PER_RUN
LLM_DATA_REGION
LLM_PROVIDER_DPA_REF
```

- 兼容服务对结构化输出的支持程度不一致，所以 `LLM_STRUCTURED_MODE` 可以切换。无论用哪种模式，返回内容都要经过 Pydantic 校验；校验失败最多重试一次，仍失败就标记该候选为“AI 判断失败”，不影响其他候选。
- 每次调用记录模型名、prompt 版本、token 用量，写入 `usage_ledger`。
- 切片只有两个 AI 任务：推荐判断和拍摄包生成。prompt 与 schema 放在 `modules/<域>/prompts/`，带版本号，版本写入 `matching_runs` / `content_brief_versions`。
- 切片不用 embedding。以后接 RAG 时再增加 `EMBEDDING_BASE_URL` / `EMBEDDING_MODEL` / 维度配置。

### 5.4 异步执行

接口在同一事务中写入 `jobs`（带幂等键），然后返回 202。后端进程内的任务执行器（若干工作线程）按租约领取任务执行，执行中定期续约并检查取消请求；应用关闭或崩溃后，下次启动时把中断的任务按任务类型重新排队或标记失败。任务类型字段已按 `ingestion / matching / media_analysis / external_actions / maintenance` 定义，以后可按类型限制并发。

### 5.5 文件与视频

文件保存在数据目录下的 `files/`，按 SHA-256 命名去重，以 `(round_id, sha256)` 唯一约束防止重复登记。界面通过本机后端上传和读取（带访问令牌），不经过任何云存储。视频播放器支持点击时间码跳转并添加反馈，AI 视频分析以后以 `media_analysis` 任务的形式加入。

### 5.6 本机安全

- 单机单用户，不做登录和多企业隔离；数据隔离依靠 Windows 用户账户（数据在 `%LOCALAPPDATA%\TKWorkspace\`）。
- 本机接口只监听 `127.0.0.1`，每次启动由外壳生成随机访问令牌，并校验 Host，防止浏览器网页或局域网访问。
- FastMoss Key、大模型 Key 存 Windows 凭据管理器；寄样地址等个人数据字段加密保存，数据密钥同样放在凭据管理器。
- 详见 [桌面版架构方案](桌面版架构方案.md) 第 5 节。

### 5.7 合作与寄样（M3，2026-09-29）

单机单用户，不设 owner 列；表名和状态值沿用 [02 · 数据模型](architecture/02-data-model.md) 7.1–7.3，只取切片需要的列。

**表（迁移 0004）**

| 表 | 作用 | 要点 |
|---|---|---|
| `creator_decisions` | 候选决定（追加事件） | `keep / needs_verification / exclude / reconsider` + 原因 + 说明 + 引用的评价；当前决定 = 每个（任务站点, 达人）最新一条。“保留”只表示值得推进，不触发任何动作 |
| `creator_relationships` | 我与某达人的长期关系 | 每个达人一条；`active / paused / archived`；与具体产品合作分开 |
| `collaborations` | 一次具体合作 | 关系 + 任务站点 + 产品版本；`planned → contacting → negotiating → agreed → in_progress → completed / closed`；同一关系在同一任务站点只有一条 |
| `collaboration_events` | 合作状态历史 | 每次推进、达成约定、关闭都追加一条 |
| `sample_shipments` | 寄样单 | 明细（SKU、数量、样品成本、币种）、费用上限；收件信息和单号是**密文列**；生命周期 `draft / awaiting_confirmation / confirmed / dispatched / cancelled` 与签收状态 `unknown / in_transit / delivered / exception / returned` 分开 |
| `shipment_events` | 物流节点（人工登记） | 追加保存，按发生时间投影当前签收状态；不能用登记顺序覆盖事实时间 |
| `external_actions` | 对外动作 | `action_kind=sample_shipment`；`payload_version / payload_hash`；状态沿用 02 的 9 个值 |
| `action_confirmations` | 本人确认 | 冻结的摘要（不含地址明文）+ 哈希；`expires_at / consumed_at / revoked_at` |

**寄样流程与防重复**

1. 创建寄样单（需要 `Idempotency-Key`；合作必须已“达成约定”）：保存为草稿，收件信息立即加密。
2. `confirmation-preview`：冻结当前内容，返回核对摘要和 `payload_hash`，状态变为“待确认”。它本身不执行任何动作。
3. `confirm`：提交看到的 `payload_hash` 和 `payload_version`（需要 `Idempotency-Key`）。哈希不一致（内容已变）则拒绝。同一个 key 重放返回同一结果；换 key 再次确认同一版本返回“已确认”，不产生第二个确认。
4. 修改收件信息、明细或费用上限：`payload_version + 1`，撤销现有确认，退回草稿，必须重新核对确认。
5. `register-dispatch`（人工登记“已寄出”，需要 `Idempotency-Key`）：要求有效且未使用的确认，使用后标记 `consumed`，对外动作记为 `succeeded`（`mode=manual`，不伪装成调用了物流接口）。已寄出后再登记返回 409，**不会重复寄样**。合作随之进入 `in_progress`。
6. 签收：只由人工登记的物流节点决定。没有节点时一直是“签收未知”，不因时间推移自动变成已签收。

`payload_hash` 用数据密钥做 HMAC-SHA256（输入含收件信息明文），避免用哈希反推地址。确认有效期 7 天，过期需重新确认。

**个人数据加密**（`platform/crypto`）

- AES-256-GCM；数据密钥 32 字节，首次使用时生成，存 Windows 凭据管理器（`pii_data_key`），不进数据库、文件和日志。
- 密文格式 `v1:` + base64（nonce + 密文），附加数据（AAD）绑定“表.列:行 ID”，密文被挪到别的行会解密失败。
- 列表和详情只返回脱敏摘要（如 `J*** · SW1A *** · GB`）；完整收件信息只有单独的 `GET /shipments/{id}/recipient` 返回，供 BD 复制填写快递单。
- 数据库文件单独拷到别的电脑，没有该 Windows 用户的凭据就读不出地址；**凭据丢失时地址也无法恢复**（需要重新填写）。
- 日志、错误信息和大模型请求都不包含收件信息；验证错误只返回字段位置，不回显输入。

**接口（`/api/v1`）**：`POST/GET /campaign-markets/{cm}/creator-decisions`，`POST /campaign-markets/{cm}/collaborations`，`GET /collaborations`，`GET /collaborations/{id}`，`POST /collaborations/{id}/transitions`，`POST /collaborations/{id}/confirm-agreement`，`POST /collaborations/{id}/shipments`，`PUT /shipments/{id}`，`POST /shipments/{id}/confirmation-preview`，`POST /shipments/{id}/confirm`，`POST /shipments/{id}/register-dispatch`，`POST /shipments/{id}/events`，`POST /shipments/{id}/cancel`，`GET /shipments/{id}/recipient`。

**界面**：推荐卡增加“保留 / 待核实 / 排除”和“准备合作”；新增“合作”页（列表 + 详情：状态推进、记录双方约定、寄样卡）。寄样卡按状态只显示当前可做的一步，确认前展示冻结摘要。

**主要错误码（409 / 422 / 503）**：`decision_required`（没有标记“保留”就准备合作）、`agreement_required`（没有记录双方约定就寄样）、`recipient_required`、`not_confirmed`、`already_confirmed`、`confirmation_expired`（过期的确认会被作废，寄样单退回草稿）、`already_dispatched`、`not_dispatched`、`idempotency_conflict`、`pii_key_unavailable`（503：本机凭据管理器里找不到个人数据密钥，例如把数据库复制到了另一台电脑——此时收件信息无法解密，其他功能不受影响）。

**前端路由**：`/collaborations`（我的合作，按状态筛选）、`/collaborations/:collabId`（详情）；侧栏新增“我的合作”。

**验收脚本**：`scripts/m3_acceptance.py`（全新临时数据目录 + 人工导入候选，不花 FastMoss 额度），逐条检查完成标准，共 15 项。
