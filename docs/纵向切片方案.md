# 纵向切片方案：一名 BD 跑通“找人 → 寄样 → 两条视频 → 分类维护”

版本：1.1 · 日期：2026-09-29 · 状态：已确认，M0 实施中

修订说明：1.1 将数据来源改为 FastMoss MCP 为主，站点范围扩展为全部欧洲 TikTok Shop 市场，并写入 2026-09-29 使用试用 Key 的实测结论。

依据：[最终产品规格](product/final-spec.md)、[架构总入口](architecture/README.md) 及 `docs/architecture/00`–`06`。本文件只规定第一条可运行路径的范围和顺序，不改变架构文档中的统一契约；两者冲突时以 [00 · 架构决策与统一契约](architecture/00-decisions.md) 为准。

## 1. 已确认的前提

| 事项 | 决定 |
|---|---|
| 目标站点 | 全部欧洲 TikTok Shop 市场（见 3.1）。每个找人任务选择一个欧洲站点，切片内不做跨站点聚合 |
| 大模型 | OpenAI 兼容接口（`base_url` + `api_key` + 模型名可配置） |
| 本机环境 | Windows + Docker Desktop + WSL2 |
| 前端 | React + TypeScript + Vite；组件库默认 shadcn/ui + Tailwind；包管理默认 pnpm |
| 后端 | Python 3.12 + FastAPI + SQLAlchemy 2 + Alembic；包管理默认 uv |
| FastMoss 接入 | **MCP 为主**（远程 Streamable HTTP）。REST 作为以后可增加的第二个适配器；CSV 人工导入用于无数据站点 |

## 2. 目标与原则

**目标**：用最短路径让 [E2E-01 一个 BD 完成两条新视频并维护达人](architecture/06-verification-and-traceability.md) 在真实代码里走通。前端、后端、数据库、Worker、模型各打通一条线，不追求每个功能模块完整。

**可扩展性原则：后补代价高的现在就做对，后补代价低的先不做。**

| 现在必须做对（以后改要大量返工） | 先简化或推迟（以后按模块加入） |
|---|---|
| `tenant_id` + `owner_principal_id` + PostgreSQL RLS | 注册、邀请、账号恢复、多企业切换 |
| 版本化与不可变快照（产品、条件、推荐、脚本、视频版本） | 文档解析与 RAG 资料库 |
| `jobs` + `outbox` + Worker 租约，队列只传 `job_id` | 调度器、周期刷新、通知 |
| 连接器注册表（固定操作 + schema + 费用） | REST 适配器、多供应方、字段能力矩阵界面 |
| 幂等键 + `action_confirmations`（对外动作由本人确认） | 自动外发渠道（切片内用“人工发送并登记”） |
| 三态硬条件 `pass/fail/unknown`；适配度与证据充分度分开 | 多种发现方式、参考达人扩展、比较视图 |
| 金额 NUMERIC + 币种；时间 UTC + IANA 时区 | 跨站点聚合、汇率换算 |
| 市场目录表 `markets`（平台站点码与供应方地区码分开） | 更多非欧洲站点（加一行目录数据即可） |
| 拍摄轮次与视频版本分开：返修 = 新版本，新视频 = 新轮次 | 受限提交链接、AI 视频分析 |
| 个人数据字段加密与最小化（寄样地址等） | 完整的数据主体请求、删除与导出流程 |
| `usage_ledger` 基本记账 + 单次运行费用上限 | 预占、结算、核对，套餐和账单 |
| 统一运行状态枚举（全部 8 个值先定义好） | 取消后恢复、partial 核对的完整界面 |
| OpenAPI 自动生成 TS 客户端 | 报表、导出、经验规则、数据删除链路 |

判断标准：只要一项会影响**数据库主键和外键、权限边界、历史可追溯、个人数据处理或外部动作的幂等**，就进入切片。

## 3. 欧洲站点处理

### 3.1 市场目录（种子数据，含 2026-09-29 实测）

[02 · 数据模型](architecture/02-data-model.md) 规定站点码“来自平台市场目录，不自动等同 ISO 国家码”。切片建立全局目录表 `markets`，把平台站点码、FastMoss 地区码、币种、时区、内容语言和数据状态分开存放。

实测方法：`creator_search`，条件 `is_ecommerce_creator=true`，按 `day28_gmv` 降序，每站 1 次。

| market_code | 站点 | FastMoss `region` | 实测结果数 | 返回的 `currency` | 结算币种 | 默认时区 | 常见内容语言 | 切片状态 |
|---|---|---|---|---|---|---|---|---|
| `UK` | 英国 | `GB` | 2000（上限） | GBP | GBP | Europe/London | en | 可查询 |
| `DE` | 德国 | `DE` | 2000 | EUR | EUR | Europe/Berlin | de | 可查询 |
| `FR` | 法国 | `FR` | 2000 | EUR | EUR | Europe/Paris | fr | 可查询 |
| `IT` | 意大利 | `IT` | 2000 | EUR | EUR | Europe/Rome | it | 可查询 |
| `ES` | 西班牙 | `ES` | 2000 | EUR | EUR | Europe/Madrid | es | 可查询 |
| `NL` | 荷兰 | `NL` | 2000 | 空 | EUR | Europe/Amsterdam | nl | 可查询，金额币种未知 |
| `BE` | 比利时 | `BE` | 1252 | 空 | EUR | Europe/Brussels | nl / fr | 可查询，金额币种未知 |
| `AT` | 奥地利 | `AT` | 775 | 空 | EUR | Europe/Vienna | de | 可查询，金额币种未知 |
| `PL` | 波兰 | `PL` | 2000 | 空 | PLN | Europe/Warsaw | pl | 可查询，金额币种未知 |
| `PT` | 葡萄牙 | `PT` | 2000 | 空 | EUR | Europe/Lisbon | pt | 可查询；TikTok Shop 是否已开放待确认，界面提示 |
| `IE` | 爱尔兰 | 无 | 0 | - | EUR | Europe/Dublin | en | 仅人工导入 |

规则：

- 任务只保存 `market_code`，调用连接器时再通过目录映射成供应方地区码。**英国必须传 `GB`**：工具说明的示例写 `UK`，但实测传 `UK` 返回 0 条且不报错，容易被误认为“没有达人”。以后接入其他供应方，只需给目录加一列映射，任务数据不变。
- 目录里标为“仅人工导入”的站点，连接器直接拒绝调用，不发出注定为空的请求。
- 返回的 `currency` 按原值保存。为空时金额显示为“币种未知”，不默认当作站点结算币种，也不做换算。
- FastMoss 的 `region` 指**达人所在地区**，不证明达人具备该站点的带货资格。推荐卡上的“带货资格”默认显示为 `unknown`。
- “实测结果数”只说明当天有数据，不代表字段完整；各站点标为“已支持”前仍需完成 M2 的契约测试。
- 一个产品可以针对不同欧洲站点各建一个任务，条件和名单互不影响（规格第 2 节）。

### 3.1a 实测发现的数据质量问题与处理规则

| 现象（2026-09-29 实测） | 处理规则 |
|---|---|
| 同一字段有时是整数、有时是小数（如 `day28_gmv`） | 统一解析为 Decimal；保存原始类型标记 |
| 按 `day28_gmv` 降序时，GB、DE 首条的 GMV ÷ 销量约为每件 9.7 万 GBP / 17.8 万 EUR | 合理性检查：折算单价超出品类合理区间时，观测标记 `anomaly`，推荐卡显示“数据异常，待核实”，不参与排序分数 |
| `total_units_sold = 0` 但 `video_units_sold > 0` | 字段间一致性检查，矛盾时两者都标记 `inconsistent` |
| 多个站点 `engagement_rate_percent = 0` | 0 视为“可能缺失”，按 `unknown` 处理，不当作真实的 0 |
| 部分站点 `currency` 为空 | 金额保存为“币种未知” |
| 空结果与失败都不扣费，但返回形态不同 | 空结果记为 `empty`，错误记为 `failed`，额度不足（402）记为 `insufficient_credits`，界面分别说明 |

排序不能只按单一金额字段降序取前几名，否则异常值会排在最前；发现阶段先取候选池，再经过合理性检查和三态硬条件后排序。

### 3.2 多语言

- `content_brief_versions` 记录 `content_language`，默认取站点的常见语言，BD 可以修改（例如比利时可选 nl 或 fr）。
- 拍摄包先生成目标语言版本，同时附一份中文对照供 BD 检查；发给达人的只有目标语言版本，并以 BD 确认的版本为准。
- 推荐理由和反馈建议默认用中文展示给 BD；发给达人的反馈由 BD 选择语言后生成草稿，确认后再发送。

### 3.3 GDPR 与个人数据（切片最低要求）

欧洲达人的联系方式和寄样地址属于个人数据，从切片起就要做到：

- 寄样地址、电话、邮箱只存在专门字段里，使用应用层加密（信封加密，本地开发用环境变量里的密钥，生产换 KMS）。日志、LLM 上下文和错误信息里都不出现这些字段。
- 发给模型的内容只包含必要信息：推荐判断用公开指标和产品资料，拍摄包用产品版本和达人公开的内容风格，不发送地址和联系方式。
- 模型服务商的数据处理地区和保留政策作为配置项记录（`LLM_DATA_REGION`、`LLM_PROVIDER_DPA_REF`）。上线前确认是否满足企业的 GDPR 要求，切片阶段不作合规承诺。
- 删除达人关系时，个人数据字段必须能单独清空；完整的删除链路以后按 [05 · 安全与运营](architecture/05-security-operations.md) 实现。

## 4. 切片范围：用户能完成的 10 步

每步对应架构中的模块和主要数据表，未列出的表不建。

| 步 | 用户动作 | 模块 | 主要表 |
|---|---|---|---|
| 1 | BD 登录（种子数据：1 企业、1 管理员、2 BD） | identity | `tenants` `principals` `memberships` |
| 2 | 填写产品和欧洲站点价格，确认版本 | knowledge | `products` `product_versions` `product_market_terms` |
| 3 | 选择一个欧洲站点建找人任务，设条件与费用上限 | campaigns | `markets` `campaigns` `campaign_markets` `criteria_versions` |
| 4 | 启动匹配，查看进度与推荐卡 | matching / connections | `matching_runs` `jobs` `outbox_events` `provider_calls` `provider_snapshots` `candidate_evaluations` `evidence_items` `recommendation_snapshots` `recommendation_items` `usage_ledger` |
| 5 | 保留或排除候选，确认合作 | shortlists / creators / collaborations | `shortlist_decisions` `creators` `creator_relationships` `collaborations` |
| 6 | 确认寄样（人工登记物流与签收，地址加密保存） | collaborations | `sample_shipments` `external_actions` `action_confirmations` |
| 7 | AI 生成目标语言拍摄包，编辑后确认 | production | `content_briefs` `content_brief_versions` |
| 8 | 第 1 轮：上传 V1 → 按时间码给反馈 → 上传 V2 → 验收通过 | production | `production_rounds` `video_assets` `video_versions` `video_reviews` `feedback_items` |
| 9 | 按几个维度分类达人，建维护计划 | creators | `creator_classification_events` `maintenance_plans` |
| 10 | 从维护计划发起第 2 轮，回收新视频；工作台显示待办 | production / automation（只做查询） | 复用以上表；待办由当前状态实时计算 |

**切片验收标准**（从 E2E-01 删减而来）：

1. 两轮计为 2 条新视频，第 1 轮的 V1/V2 只算 1 条。
2. 旧脚本、旧反馈和旧视频版本都能查到。
3. BD-B 看不到 BD-A 的关系、合作、地址和视频（RLS 集成测试）。
4. 重复提交同一个幂等请求，不会重复寄样、重复调用付费接口，也不会重复产生视频。
5. 未知字段在推荐卡上显示为“未知”，不被当作 0 或“符合”。带货资格默认未知。
6. 英国任务显示 GBP、Europe/London，德国任务显示 EUR、Europe/Berlin，两个任务的名单互不影响。
7. 日志和 LLM 请求记录中查不到寄样地址。

## 5. 关键技术决策

### 5.1 数据来源：FastMoss MCP 连接器

**接入方式**：后台 Worker 作为 MCP 客户端，按固定工具清单调用 `https://mcp.fastmoss.com/mcp`（Streamable HTTP）。**不让大模型自己选择 FastMoss 工具**，符合 [00 · 架构决策](architecture/00-decisions.md) ADR-05。

连接器接口 `ProviderOperation`：`name`、`params_schema`、`response_schema`、`credit_cost_estimate()`、`execute(ctx, params)`。内部操作与 MCP 工具的对应关系：

| 系统内部操作 | MCP 工具 | 实测 / 预计扣费 | 阶段 |
|---|---|---|---|
| `account.credits` | `credit_usage_summary` | 0（实测） | M0 连通检查 |
| `creator.search` | `creator_search` | 每次 1 额度，与返回条数无关（实测） | 切片 M2 |
| `creator.profile` | `creator_profile_overview` | 预计 2 额度 | 后续 |
| `creator.audience` | `creator_fans_distribution` | 预计 2 额度 | 后续 |
| `creator.content` | `creator_video_analysis` | 预计 2 额度 | 后续 |
| `creator.products` | `creator_product_list` | 预计 1 额度 | 后续 |
| `video.script` | `video_script_info` | 待实测 | 后续（拍摄参考） |

实测得到的接口规则（2026-09-29）：

- 认证用请求头 `Authorization: Bearer <key>`，**不把 Key 放进网址**；服务器返回 `mcp-session-id`，连接器负责会话建立与失效重连。
- 服务器共 55 个工具，都没有 `outputSchema`；结果是 `content[0].text` 里的 JSON 字符串。连接器必须用自己的 Pydantic schema 校验，校验失败时该能力降级，不把解析不了的数据当成 0。
- 每次结果带 `_meta.charge = {charged, credit_cost, remaining_credits}` 和 `request_id`，直接写入 `provider_calls` / `usage_ledger`，余额显示以它为准。
- 每页最多 10 条，`page` 最大 500，`total` 显示上限 2000。每次调用扣费与条数无关，所以固定取 `pagesize=10`。
- 空结果不扣费；额度不足返回 402，按 `insufficient_credits` 处理并提示充值，不自动重试。
- 限速按套餐（试用和 Basic 为每分钟 40 次）。连接器在 Redis 中做按 Key 的令牌桶限流，超过时排队，不并发冲击。
- 每取一页前都检查任务费用上限和取消状态。

其他适配器：

- **`FastMossRestAdapter`**（以后）：REST 价格按条数计费，大批量搜索时可能更便宜。它与 MCP 实现同一个 `ProviderOperation` 接口，任务按连接能力选择**一种**传输方式，同一逻辑请求不会两条路都试。
- **`ManualImportAdapter`**：导入 CSV 达人名单，用于爱尔兰等没有数据的站点，或者没有 Key 时开发。发现方式记为 `manual_import`，界面提示“非实时数据”。
- **`FixtureAdapter`**：只在 `test` 环境注册，生产配置启动时拒绝加载。自动化测试使用它，不消耗额度。

合规：FastMoss 条款要求对数据保密，不得分享、转让或用于竞品。切片期间不缓存原始响应，只保存规范化快照；多企业共用、云端 LLM 处理和缓存的正式授权在商用前向 FastMoss 书面确认。

### 5.2 匹配流程：用 LangGraph 做最小图

```text
load_context → discover → hard_filter → assess(LLM) → validate → persist
```

- `hard_filter` 是纯代码，只输出 pass/fail/unknown，不交给模型。
- `assess` 用结构化输出，每条判断必须引用 `evidence_id`；`validate` 删掉引用不存在的结论，并标记为模型推断。
- checkpoint 存在 PostgreSQL（`langgraph-checkpoint-postgres`），只保存执行位置和对象引用，不复制业务数据。
- 以后要加的节点（`enrich` 补查详情、RAG 检索、`waiting_input` 暂停）都插在现有节点之间。

### 5.3 模型：OpenAI 兼容接口

- `platform/llm/gateway.py` 统一封装 `langchain_openai.ChatOpenAI(base_url=..., api_key=..., model=...)`，业务代码只调用 gateway。
- 配置项：

```text
LLM_BASE_URL          例：https://api.openai.com/v1 或任意兼容服务
LLM_API_KEY           本地开发放 .env，生产放密钥存储
LLM_MODEL_MATCHING    推荐判断使用的模型
LLM_MODEL_BRIEF       拍摄包生成使用的模型
LLM_STRUCTURED_MODE   json_schema | function_calling | json_mode
LLM_TIMEOUT_SECONDS
LLM_MAX_TOKENS_PER_RUN
LLM_DATA_REGION
LLM_PROVIDER_DPA_REF
```

- 兼容服务对结构化输出的支持程度不一致，所以 `LLM_STRUCTURED_MODE` 可以切换。无论用哪种模式，返回内容都要经过 Pydantic 校验；校验失败最多重试一次，仍失败就标记该候选为“AI 判断失败”，不影响其他候选。
- 每次调用记录模型名、prompt 版本、token 用量，写入 `usage_ledger`。
- 切片只有两个 AI 任务：推荐判断和拍摄包生成。prompt 与 schema 放在 `modules/<域>/prompts/`，带版本号，版本写入 `matching_runs` / `content_brief_versions`。
- 切片不用 embedding。以后接 RAG 时再增加 `EMBEDDING_BASE_URL` / `EMBEDDING_MODEL` / 维度配置。

### 5.4 异步执行

API 在同一事务中写入 `jobs` + `outbox_events`，然后返回 202。Dispatcher 轮询 outbox 投递给 Celery；Worker 领取租约后执行。切片先用一条 `default` 队列，但任务类型字段已经按 `ingestion / matching / media_analysis / external_actions / maintenance` 定义，以后按字段拆队列即可。

### 5.5 文件与视频

S3 兼容存储，开发环境用 MinIO。上传流程是预签名 URL → 完成回调时校验 SHA-256，以 `(round_id, sha256)` 唯一约束防止重复。视频播放器支持点击时间码跳转并添加反馈，AI 视频分析以后以 `media_analysis` 任务的形式加入。

### 5.6 权限

- 每个请求建立 `ExecutionContext`，并在 DB 会话里执行 `SET LOCAL app.tenant_id / app.principal_id`。
- 业务表启用 `FORCE ROW LEVEL SECURITY`；应用数据库账号不是表所有者，也没有 `BYPASSRLS`。Alembic 迁移使用另一个所有者账号。
- 私有表（关系、合作、寄样、视频等）的策略同时检查 `tenant_id` 和 `owner_principal_id`。
- 复合外键 `(tenant_id, id)` 防止跨企业关联。

## 6. 本机开发环境（Windows + Docker Desktop + WSL2）

按 [00 · 架构决策](architecture/00-decisions.md) ADR-02：Web 和 API 可以在 Windows 原生运行，Celery、Redis、PostgreSQL 使用 Linux 容器，不把 Windows 原生 Celery 当作支持环境。

| 组件 | 运行位置 | 说明 |
|---|---|---|
| PostgreSQL 18 + pgvector | Docker | 镜像版本在建仓时锁定；数据用命名卷保存 |
| Redis | Docker | Celery broker；只放可丢失的数据 |
| MinIO | Docker | 本地对象存储，启动时自动建私有 bucket |
| Worker + Dispatcher | Docker | 与 API 使用同一个后端镜像，启动命令不同 |
| API（FastAPI） | Windows 原生（uv）或 Docker | 开发时建议原生运行，热重载快 |
| Web（Vite） | Windows 原生（pnpm） | 通过 Vite proxy 访问 `/api`，前端不写死后端地址 |

约定：

- 项目根目录初始化 Git 仓库；`.env`、密钥和 FastMoss 原始响应不进版本库。
- `infra/compose/compose.yaml` 用一条 `docker compose up -d` 启动全部基础服务，并带健康检查。
- 代码放在 Windows 目录时，挂载进容器的源码只供 Worker 在开发时热重载；数据库和 MinIO 的数据只用命名卷，不挂载 Windows 目录，避免跨文件系统的性能和权限问题。
- 仓库使用 LF 换行（`.gitattributes` 统一设置），避免 Windows 和 Linux 容器之间出现脚本换行问题。
- `.env.example` 只列变量名；真实 `.env` 不进版本库。

## 7. 工程结构（完整目录的子集，模块名不变）

```text
apps/web/src/
  app/                    路由、会话、布局
  features/
    workbench/            我的待办
    products/  campaigns/  matching/  creators/  production/
  lib/api/                OpenAPI 生成的客户端
backend/src/tk_workspace/
  api/                    FastAPI 入口、中间件、错误格式
  modules/
    identity/ knowledge/ campaigns/ connections/ matching/
    creators/ shortlists/ collaborations/ production/
    # learning/ automation/ reporting/ billing/ 以后再建，不建空目录
  platform/
    db/  jobs/  outbox/  storage/  secrets/  llm/  crypto/
  workers/
  integrations/fastmoss/
backend/migrations/       Alembic（含 markets 种子数据）
backend/tests/unit/ integration/ e2e/
infra/compose/            postgres(pgvector) + redis + minio + worker
```

每个模块统一分层：`models.py`（ORM）· `schemas.py`（Pydantic）· `service.py`（业务规则）· `router.py`（HTTP）· `repo.py`（查询）。模块之间只能调用对方 `service` 的公开函数，不能直接查询对方的表。
